# Turn a case into a useful judgment

Use the [shared writing standard](../../../docs/experience-authoring-standard.md) for the tone and evidence conventions, and the [contribution interface](../../../docs/experience-usage-interface.md) for tools and authority. This Skill helps a task contributor or an explicitly assigned analyst think; it grants no permission to rewrite the library or its manuals.

Start from the distinction that changes a decision. A useful experience explains why a plausible design failed, why a neighboring case differed, and which condition should favor a different choice. Lead with the practical preference. A sequence of events or a reminder to consider all risks adds little.

Read the nearest current account and a representative entry from the same layer before drafting. The maintenance context supplies writing references from its frozen private library. Follow their level of explanation: **name the action, explain what in the scene or renderer makes it work, and show how to express or inspect it**. For example, the emission account teaches the relation between the glowing perimeter and its unlit support; "check whether the light is correct" would lose the useful judgment. Keep a recommendation direct even when its evidence is a small set of cases, and identify that evidence in the footer. Use the case to develop a new judgment, not to copy its objects into a new task.

## Place the judgment before writing it

The library is layered. A judgment belongs in one of three: a **principle** that holds across renderers (about recasting itself), a **renderer** capability or trap (what Bernini or Ditto did under a given construction), or a **condition** of the task (short or long request, family of world or medium). Decide the layer first, and state the evidence status: train-split cases only, scores from the current evaluation protocol, how many tasks, how many renderings per condition. Evidence on one task is a working pattern; evidence on none is a hypothesis, and says so. Do not use held-out (test-split) videos, their scores or their prompts.

## Understand the objective behind the attempt

Compare the user's request, source performance, Planner's added commitments and the reviewer's interpretation. An exact prompt can pursue the wrong event. Retaining an obsolete source activity can defeat a world transformation; replacing it can be the intended achievement. A task is scored on how fully the world was rebuilt, whether the moment is recognizable, and how stable and clean the video is; describe methods that move these, and keep judge rubric details out of the guidance. Decide what the target needs before explaining a difference as damage.

Historical requirements and scores are attributed judgments. Keep their observations while revising a mistaken interpretation. The [semantic goal review](../../../knowledge/experience/curated/evidence/semantic-goal-review-20261102.md) illustrates this operation without making its particular adaptation a genre rule.

## Explain the contrast through the actual construction

Read the selected input and exact submitted prompt. Distinguish a missing instruction from an explicit instruction that failed, visual ornament from the requested structure, and a changed construction from stronger wording. An input carries a particular person's appearance, an activity, spatial relationships and existing gains; identify which of these made continuation useful or obstructed the next transformation.

Inspect useful and failed outcomes. Find the scene-level relationship behind the contrast: clothing covering a necessary contact, a theme retaining the old location's function, a global color treatment dominating skin, or a candidate repair constructing another object. Recommend a compatible realization or a better-supported input. Develop a renderer-specific working preference when that is the useful increment; support it with the actual setup and counterexamples.

Use the recorded continuation question, answer and subsequent action to locate the distinction Planner claimed to rely on. Check whether the dispatched prompt and input implemented it. Follow the result into the next choice. A sound judgment followed by failed execution calls for a different lesson from a mistaken explanation. Budget notices describe the decision setting, not an empirical stopping law.

## Contribute an account the next Planner can use

State the condition, preference and explanation in natural prose. Keep action-changing boundaries beside the advice; put counts, source events and protocol details in the evidence footer. Distinguish a proposed repair from an observed successful repair once, clearly. Use counterexamples to refine the condition and retain successful choices as well as failures.

Use saved-video observation for a new visual claim, or attribute an existing review. Separate frames seen online from frames inspected after the task. Sparse evidence can leave an event unresolved while supporting a local judgment. Consult the [observation contract](../../../docs/online-event-observation.md) when temporal coverage matters.

Create a new contribution when it offers a distinct explanation. For an existing account, add a clarification, recommendation, counterexample comment or exact proposed revision. Link the relevant entry; runtime binds its version and the source case. State no increment when the case adds none. A new conditional recommendation can be useful immediately in the contribution layer; replacing the canonical account is a separate curation decision.

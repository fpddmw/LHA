## Continuation and factual resource use

`src/planner_harness/continuation.py` owns the operator policy, receipt-based spending projection and passive decision records. The [2026-11-02 fixed-budget update](creative-generation-budget-v2.md) gives new Loops a shared maximum of five distinct signed render submissions. The first two submissions allow free exploration. Definite failures and uncertain submissions count toward that same budget and reminder schedule; recovery of an unchanged signed job consumes no additional slot. Imported media consumes neither this task's submission allowance nor its paired successful-generation seed index.

`generate` accepts `justification`. Once requested, any nonempty string passes, including a weak or repeated string. Missing/blank text returns the three stable questions and creates no job, request charge or seed use. A compliant response includes actual input, prompt and explanation together. No semantic evaluator, additional approval model, usefulness grade, keyword requirement or regression scoreboard is used. The explanation is recorded beside the signed request, and is absent from the renderer payload and neutral Critic packet.

The operator-only `creative-continuation-v2` policy uses `free_requests=2`, `deliberate_after_requests=3`, `strong_after_requests=4` and a maximum `hard_generation_limit=5`. New full/none cohort manifests share this limit; smaller explicit caps remain available for software fixtures or operator restrictions. Null selects the finite default. A configuration above the approved maximum is rejected. Reminders express increasing restraint without disclosing thresholds, percentages, total or remaining allowance. At the limit, the projection switches to closure guidance and stops asking for generation explanations. This is a runtime policy, not a measured quality improvement.

Locking refuses only new `generate` requests and leaves inspection, reading, Critic and the entire delivery-confirmation sequence usable. Reopening a model-call/time resource pause preserves the generation cap instead of adding more render slots. Existing whole-task protections remain separate; a generation lock alone neither declares success nor settles an incomplete task. Old frozen runs retain their recorded protocol and require explicit migration before this runtime resumes them; no historical state is migrated by changing the source files.

The model projection supplies generated/submitted counts, definite failures, uncertain/pending attempts, cumulative known rendering wall time, missing cost records, current generation availability, the visible pressure text and whether the explanation is required. It does not include policy version/stage, thresholds, total/remaining allowances, ratios or disabled-limit facts. Creative context always goes through the projection, including an old context-version marker; renderer/role settings are explicitly selected rather than dumped. Historical visual content and model-authored evidence are retained verbatim.

`calls/<event>/continuation-policy.json` stores the exact saved model-input hash, operator policy, stage, trigger state and visible text. `jobs/<job>/continuation.json` binds the exact explanation to actual input/prompt and signed job. `render_outcomes` records returned statuses. `continuation-index.json` and the existing per-arm/batch archive pages provide passive navigation to explanations, prompts, receipts and candidate outcomes without causal attribution.

## Review reuse and actual Planner confirmation

`src/planner_harness/delivery_review.py` implements `creative-delivery-review-v3-auto`.

The first satisfied `finish` always creates a proposal. A previously collected, valid online report can be reused only after checking the original signed job, candidate/source/request identities, frozen Critic profile/model, original model input and answer, evidence bytes and fixed report validation. Its legitimate focus, comparisons, supplemental checks and requested events remain unchanged. Independent GLM/Sonnet final reports are outside this lookup. Every successful generation already queues its online report before Planner resumes. Missing or failed reports retain the original automatic job for reconciliation; finish creates no replacement review. Neutral focus is supplied with generate.review_focus and excludes renderer prompt/Planner justification.

The reuse path puts the complete report and current proposal identity in a subsequent saved Planner input. Runtime exposure records bind that input to the exact report. Confirmation checks the real transport input and returned Planner response, a distinct post-proposal event, selected media, report and input hashes. It retains the existing nonempty `message`; no keyword-based tradeoff detector or additional acknowledgment form is applied. Low/unknown scores impose no grade threshold.

Read/observe/note can continue. A changed delivery choice or submitted generation supersedes the proposal. A later proposal may reuse the same unchanged valid report, but receives a new post-proposal exposure and decision. An unanswered or failed review remains incomplete and retains its original job/attempts. Same-proposal interruption recovery reuses completed stages and preserves the original request and attempt records.

The shared verifier in `delivery.py` rechecks this chain. `experiments/creative_benchmark.py::verify_arm` requires the matching creative task and verified confirmation before the topic/archive gate accepts a Loop receipt. Direct remains unchanged. The original five independent-scoring positions, blinded input/rubric/model identities, cache identity and unscored-intermediate archive behavior remain in force.

## Versioned migration preparation; live pause retained

`scripts/prepare_creative_protocol.py` writes plans and never applies state, calls a model, dispatches a render or restarts polling. `--run` prepares a settled-run transition; `--baseline-batch` plus `--baseline-profile` prepares a distinct target-profile/diff package from saved snapshots without inspecting the host.

The local apply primitive in `protocol_migration.py` requires explicit separate authorization and unchanged plan/prefix hashes. It rejects unsettled Planner calls and unresolved tool outcomes. An existing final tool receipt can stay pending collection; its signed request/response and seed remain unchanged. Old state, system instructions, final and mutable report files are snapshotted; old immutable calls/events/jobs/videos and the exact knowledge snapshot retain their hashes. New runtime/profile/manual identities and a migration event are recorded. A completed Loop reopens its prior selected video as a proposal, retaining the old final and obtaining a new actual Planner decision; rerendering is conditional on Planner's later choice.

The paused real batch has not been migrated or re-inspected. Its original runtime/profile fingerprints remain intact. Actual resumption still needs explicit user authorization, settled-receipt/ownership inspection, preservation of the frozen checkout, and versioned batch/service bindings to the new profile. Existing strict fingerprints intentionally reject simply running changed code against the old profile. Per-run migration plans are a preparation capability, not an automatic deployment or new scheduler. Superseded completed archives must retain their old manifest before a new selection is summarized.

Preparation against the saved real baseline identified a pre-existing physical-availability difference: the frozen remote profile has 327/238 full/none items, while the local checkout has 477/337. The prior local release snapshot already has those same local totals. Every baseline item retains its exact hash; local extras are available style images and historical files. The package records those extras and labels the target `local_preview_only` / `prepared_requires_environment_reconciliation`. It does not silently approve extra knowledge or synthesize a matching fingerprint. Per-run application remains strict about scope equality; the formal target must be frozen in the original host layout after separate authorization.

## Verification scope and limits

Focused offline checks cover request-counted exploration and the exact fifth/sixth boundary; missing/weak/repeated explanations; one-response dispatch; unchanged job/seed accounting; private-policy projection; a real generation-only cap with full delivery still available; valid report reuse including comparison/focus/supplemental checks; absent/invalid report paths; actual post-proposal model-input/response linkage; low/unknown confirmation; supersession and tamper rejection; active/completed prefix migration; and the existing topic gate, independent judges, recovery and portable archives.

These checks establish software behavior over mocks/saved media. They do not establish that pressure improves model choices or that a free-text explanation is useful. Explanations receive no semantic runtime assessment. These recorded checks used the evidence protocol at their checkpoint. Current question-led selection and continuous coverage are described in [event observation](online-event-observation.md); selection, segment observation and main grading are separate calls within one review. No live model or GPU validation was performed in this implementation pass.

Recorded checks: 101 creative regression executions passed (discovery includes imported fixture classes); the final boundary checks passed 11 delivery tests and 4 migration tests, and 8 continuation tests passed after the availability guard. Legacy delivery, durable-service and Planner suites passed 36, 18 and 11 executions respectively. The exact software-example inputs/proof and [verification metadata](../reports/20261101-creative-continuation-software-examples/verification.json) are retained. The final resume guard also rejects an old protocol or a fabricated completed flag instead of returning it as a current delivery.
